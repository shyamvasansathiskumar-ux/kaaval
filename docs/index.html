    Kaaval

    காவல் Tamil for guard

    Allow, ask or deny, before the agent's command runs. A permission layer between an AI coding agent and the shell, the database and its tools.

    01 · The finding

    Nobody attacked them. They broke anyway.

    Between July 2025 and April 2026, six AI agents destroyed real data with no attacker involved: a home directory, a drive, a production database during a code freeze, an inbox after the user said stop. I catalogued them in ai-incident-atlas.

    Every control that would have stopped them lives outside the model. None of them is a better prompt. Kaaval is those controls, written as code.

    AllowAskDenyBefore it runsPermissions, not prompts

    02 · Five rules

    Five failures. Five rules.

    Each rule enforces one entry of the checklist proposed in the atlas.

    01Scope widening

    The right command with an over-broad target.

    rm -rf tests/ patches/ plan/ ~/

    Every target of rm, mv, find -delete, >, dd, git clean and Windows rmdir /s is resolved the way the shell will: ~, $HOME, .., symlinks. Outside the workspace is denied. Targets that depend on runtime values go to a human.

    02Unverified precondition

    Carrying on after a step failed.

    mkdir archive ✗ failed
    mv a.md archive/a.md

    After a mutating step fails, or its post-condition doesn't hold, every further change is refused until a human runs kaaval ack. Moving several files into something that isn't a directory is refused before it runs.

    03Constraint override

    Breaking a freeze, or ignoring "stop".

    kaaval freeze on
    kaaval stop "don't touch the inbox"

    Freeze and stop change permissions, not the prompt. While either is on, nothing that changes state runs. Reads still work.

    04Credential overreach

    A staging task reaching production or the backups.

    railway volume delete pocketos-prod-db

    The workspace is bound to one environment. Commands, SQL targets and tool calls that name another (prod, live) are denied, and destructive actions that name backups or snapshots are out of reach.

    05State misreporting

    The agent's account of the damage is wrong.

    #0 4802a4… → #1 9c1f0e… → #2 51ab73…

    Every decision and real outcome goes into a hash-chained ledger. kaaval report says what happened from the record. kaaval verify catches any edited or deleted line.

    03 · The incidents, replayed

    Six refused. The narrow command still runs.

    Each damaging action, run through the real guard. 08 and 09 are verbatim from the public record; the others are reconstructions of the same shape, and say so. A guard that blocks everything isn't a guard anyone keeps switched on, so each replay also checks the intended command is allowed.

    05 · In front of Claude Code

    One hook. Every tool call.

    Kaaval answers Claude Code's PreToolUse hook. Bash commands are checked as shell. Write and Edit are checked as writes to their file path. Other tools pass through to the agent's own permission settings.

    // .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash|Write|Edit|MultiEdit",
        "hooks": [{ "type": "command",
                    "command": "python3 -m kaaval hook claude-code" }] }
    ]
  }
}
    $ pip install .
$ kaaval init --env staging
$ kaaval check -- "rm -rf build"
ALLOW  rm -rf build
$ kaaval report        # what actually happened
$ kaaval verify        # is the record intact?

    06 · What this is not

    Read this before relying on it.

    1. It's not a sandbox. It reads commands statically. A determined program can hide intent: write a script and run it, python -c, base64 into a shell. Kaaval is one layer, next to least-privilege credentials, an OS sandbox and backups the agent can't reach.
    2. The environment check is a word match. A production database called db7 won't be caught. Name your environments, or bind credentials so the agent can't reach production at all. That's the real fix.
    3. The SQL check reads keywords, not a parse tree. Good enough to catch DROP, TRUNCATE and an unbounded DELETE. Not a SQL firewall.
    4. ASK needs a human to answer. In an unattended pipeline, treat it as DENY.
